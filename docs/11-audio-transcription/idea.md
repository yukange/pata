# Idea — 阶段 11：本地音频转写为 Note

> **状态：设计已确认，待实施。** 阶段 10 提供固定北京地域的阿里云本机文件凭证；本阶段在阶段 9 的 Files 与 Notes 基础上增加语音转写能力。
>
> 核心目标：**一段 MP3，变成一篇可阅读、可复制、随时精确回听的只读逐字稿 Note。**

## 为什么要做

用户经常需要将多人会议录音整理为可检索、只读的原始逐字稿，尤其关注中文技术术语、说话人、句子级毫秒时间戳，以及随时返回原始音频核对。人工在普通转写文本和音频进度之间反复寻找位置很费力。

啪嗒无需发展为会议管理应用：转写只是**创建 Note 的另一种方式**。记录在存储和列表层仍是普通 Markdown Note，**自动生成的逐字稿正文在啪嗒界面中只读**，MP3 仍是普通文件资源。普通手写 Note（即便插入 MP3）照常编辑。

## 只需一条主流程

1. 在 Notes 的新建操作中选择「从音频创建笔记」，导入本地 MP3。
2. Pata 将原始 MP3 **复制**到 Vault 的 `files/`，不修改或移动外部原件；**文件导入成功后立即创建一篇关联音频的普通 Note**，即使云端转写未完成或失败，这篇 Note 也已存在。必要时只为上传生成临时单声道副本。
3. 使用阶段 10 的北京地域 API Key，通过阿里云百炼 `qwen-audio-3.1-asr-flash-filetrans` 异步识别，并启用说话人区分；用户切换到 Today/Tasks 时保持当前 App 进程内的转写任务。
4. 识别成功后填充**已有** Note 的正文，保留句子级 `HH:MM:SS.mmm` 时间戳、说话人和原始音频关联；直接使用 Note 的标题字段，正文不重复写入 `# 标题`。转写失败时 Note/MP3 保留，可从该 Note 重试。
5. Note 顶部是极简音频播放器：点击正文时间戳跳转原音频；拖动播放器并松开后，正文自动定位并轻微高亮对应句子。
6. 用户可以选择、复制、搜索逐字稿，但不能通过啪嗒修改识别正文、说话人或时间戳；**标题、标签等 Note 属性仍可编辑**。播放器 `···` →「重新转写」使用原始 MP3 再次识别；按已有确认流程替换整篇只读逐字稿，保留标题、标签与原始音频关联，失败不影响旧稿。

## 本阶段交付

- **一个只读逐字稿 Note**：仍使用现有 Markdown Note 数据模型与单列 Notes 列表；自动生成的转写正文使用只读 Markdown 展示，不启动可编辑正文模式，不引入 `Transcript` 顶层实体。普通 Note 编辑器不变；标题和标签可编辑。
- **一个原始 MP3**：复用阶段 9 `files/` 与标准 Markdown 文件引用；不做特殊文件管理页面。
- **一个播放器**：顶部播放/暂停、进度条、当前时间/总时长；其他交互按需利用系统能力，不做音频编辑器。
- **两个定位方向**：正文时间戳 → 播放器；播放器拖动结束 → 正文。自然播放不强制逐字稿跟随滚动。
- **一个重新转写入口**：直接使用唯一配置模型；不让用户挑模型或供应商。
- **可靠的失败保护**：从导入成功起 Note 和 MP3 就存在；上传或转写失败可从原 Note 重新发起。退出 App 后不承诺自动恢复未完成的云端任务，但不丢本地 Note；重新转写不覆盖标题、标签或主录音关联，外部文件竞争写入仍需遵守现有冲突保护。
- **音频关联与时间戳链接格式**：逐字稿只读让时间戳可以稳定地呈现为可点击链接。需要明确标识**自动生成的逐字稿 Note**，不能因为普通 Note 插入 MP3 就将其锁定；主音频的 Frontmatter 关联字段与时间戳 Markdown 链接具体语法仍待最终确定，确定后统一更新阶段 2 Schema，不另建侧车。

## 非目标

不做实时录音/转写、内置 AI 摘要、翻译、会议纪要、参会人管理、说话人身份库、字幕导出、音频剪辑、时间轴工作台、进度条持续强制滚动、JSON 侧车、数据库、云同步、OSS 配置、多 ASR 供应商框架及超长会议自动切换服务。
