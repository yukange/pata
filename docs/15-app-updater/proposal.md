# 阶段 15 · 应用内更新与 macOS 原生菜单 — Proposal

> 状态：**设计已确认，待实施**（2026-10-24）。产品裁决见 [idea.md](idea.md)，本文件是 015 的实施与验收主文档。**本阶段文档建立不代表代码已实现。**

## 一、现状与边界

- 目前使用 **Go + Wails v3 beta.28 + React/TS**；`main.go` 通过 `application.DefaultApplicationMenu()` 设置默认原生菜单，但尚未将「设置…」「检查更新…」明确接入业务行为。
- `frontend/src/App.tsx` 左侧边栏底部已有「设置」和仅在异常时出现的 Vault 健康入口；`SettingsView` 是现有主窗口内的辅助页面，不另开设置窗口。
- `build/darwin/Taskfile.yml` 可构建 `.app` / `.dmg`；常规本地包采用 **ad-hoc 签名**，另有开发者签名/公证任务，但尚无可供应用内更新的完整 Release 交付链。
- `build/darwin/Info.plist`、`frontend/package.json` 当前硬编码 `0.1.0`；发布时需要避免运行时版本与 GitHub Tag 分离。
- 仅实施 **macOS 官方正式安装包**的应用内更新。开发模式、本地源码构建、个人定制包不得接入官方自替换更新；不扩展 Windows/Linux 发布范围。
- 不修改用户 Vault、Markdown Schema、Agent/MCP 行为。设置页面仅新增一项「自动检查更新」开关，不新增主导航或更新管理页面。

## 二、更新流程与 UI（015-001）

### 2.1 唯一入口与触发

- **官方正式安装版**默认开启后台自动检查：启动后检查一次，运行期间每约 6 小时再检查；无更新时无更新入口和提醒，后台网络失败不弹通知。开关关闭时不再发起后台检查。开发/个人构建则从构建层禁用官方更新能力，不采用默认开启策略。
- 新版本可用时，在 App Shell 左侧侧边栏底部**设置旁**显示紧凑的「更新」按钮，保留现有 Vault 异常告警入口；窄侧栏时合理分配宽度，避免丢失设置/异常入口。
- 点击「更新」直接开始下载；**不经过查看版本、更新说明弹窗、独立更新窗口**。既有主窗口操作不中断。
- 更新相关状态在侧边栏底部唯一按钮表现；SettingsView 内只新增一行「自动检查更新」开关及简短说明，不加入版本页、更新通道或下载/安装选项。

### 2.1.1 唯一更新偏好

- 在现有 SettingsView 中新增一行「自动检查更新」，说明「发现新版本时，在侧边栏提示更新」。保持现有单页设置结构，复用基础开关样式；不添加单独的更新中心、多个配置项或版本信息卡片。
- 仅一个 Boolean 应用级偏好（建议 `auto_check_updates`），**不绑定 Vault**，不写业务 Markdown。官方正式发布版在没有记录时默认 `true`；用户修改后立即生效并持久化、重启不丢失。
- **关闭**时取消后续定时检查；未开始下载的旧更新提示隐藏。正在进行的用户主动下载/暂存/「等待安装」不因切换此开关被破坏，因为它仅控制「自动检查」，不是取消安装或下载。
- **手动检查始终保留**：macOS Pata →「检查更新…」即使自动检查关闭也可执行一次；如有新版仍显示更新按钮，用户点击才下载。
- 为照顾通过源码贡献代码的开发者，开发模式和个人/非官方构建**不得向上游发布源自动检查或自行替换**。不仅依赖默认值；构建期显式标记官方正式发布、运行时确认发布包可信及可更新。开发构建选择菜单「检查更新…」可轻量提示当前构建不支持应用内更新，升级须重新构建源码。
- 不设置名为「自动更新」但实际仅检查的误导开关；不做无人值守下载或重启。已经安装官方包的开发者可以关闭后台检查。

### 2.2 用户态

| 用户态 | 按钮文案/样式 | 触发与下一步 |
| --- | --- | --- |
| 无更新/后台检查 | 隐藏 | 检查完成后如有新版切换为更新 |
| 有更新 | Lucide 下载图标 +「更新」 | 点击开始下载 |
| 正在下载 | 下载/环形进度图标 + `XX%` | 随真实下载事件更新，避免频繁布局跳动 |
| 下载 100%，校验/暂存中 | 保留 `100%` 且处于忙碌态 | 这是短暂内部步骤，不叫「准备安装」 |
| 已暂存且草稿未保存 | Lucide 时钟图标 +「等待安装」 | 不主动退出，待用户保存/放弃后再次点击 |
| 正在执行重启 | 「正在更新」短暂状态 | 替换程序并启动新版本 |
| 下载/校验/应用失败 | 「重试更新」 | 轻量错误信息与可重试操作 |

- **百分比必须真实**：`floor(written / total * 100)`（有明确总大小时），范围 0–100。只有下载阶段展示百分比；校验和暂存不虚构安装百分比。总大小未知时仅显示不确定进度图标，不显示伪造的百分比。
- 下载成功事件并不等于可重启；必须等**校验和暂存全部成功**、收到 ready 后才执行后续操作。
- 进度和状态尽可能由 Wails 事件驱动；用户点击下载后阻止重复并发点击，错误后可重试。浅/深色、系统强调色、键盘焦点与 VoiceOver 描述沿用阶段 12 规范。

### 2.3 草稿与自动重启

- 待更新包完全就绪后，检查现有应用级草稿状态：**Note 编辑器待保存/保存中/冲突未解决**、**Task Inspector / Activity 的未提交编辑**，沿用现有草稿保护规则，不以「编辑器已打开」等同于「有未保存内容」。
- **无未保存草稿**：直接进入安装重启；调用 Wails 的 restart/apply 之前再确认一次草稿状态，避免检查与触发之间发生新编辑。
- **存在未保存草稿**：进入「等待安装」，不弹强制退出确认，不直接调用 `Restart`，用户继续工作不受影响。
- 即使自动保存后来完成，也**不自动重启**；用户点击「等待安装」时再次检查草稿，安全时才执行重启；仍未保存则给出非阻塞的「请先保存当前编辑」说明。
- 保留 Wails/应用已有正常关闭保护；更新 helper 不应绕过未提交草稿保护。用户关闭 App 后重新打开时，仍需正常检查更新；不额外开发复杂的跨启动下载续传。

## 三、Wails Updater 与发布（015-002 / 015-003）

### 3.1 技术路径

- 优先复用 **Wails v3 `app.Updater`** 和官方 GitHub Releases provider，使用 `yukange/pata` 作为唯一正式发布源。现有 beta.28 已有 `Check`、`DownloadAndInstall`、`Restart`、下载进度事件等接口；**实际落地前在 beta.28 对 headless/事件/退出方式做最小实机验证**，发现版本缺陷再评估局部升级，禁止为此整体升级无关依赖。
- **关键区分**：定时检查调用 `Check(ctx)`，不能直接依赖 `CheckAndInstall` 或可能自动触发下载的定时便利流程。更新仅在用户点击后才 `DownloadAndInstall(ctx)`，ready 后按草稿规则决定何时 `Restart(ctx)`。
- 使用 `updater.WindowNone`（经 beta.28 实测验证）禁止框架默认更新弹窗；订阅 `EventUpdateAvailable`、`EventDownloadProgress`、`EventUpdateReady`、`EventError` 等事件，传递给现有 App Shell。必要时封装一个最小 Go 服务让 React 调用检查/下载/重启，**不另写 HTTP 下载器或替换 helper**。
- 启动/菜单检查与自动定时检查共享同一状态，避免并行操作；检查定时器受已持久化的 `auto_check_updates` 控制。开发/个人自编译和 ad-hoc 本地包必须经明确的发布构建标识阻断生产更新路径（不仅比较版本字符串）。
- **术语对应**：Wails `DownloadAndInstall` 的 `install` 主要是校验、解包和暂存；**真正替换并重启**在 `Restart` 阶段。UI「等待安装」是 ready 后因草稿延迟重启，不与后台暂存冲突。

### 3.2 GitHub Release 约定

- 统一 SemVer：例如 Tag `v0.2.0` 对应 Updater `CurrentVersion = "0.2.0"`、macOS `CFBundleShortVersionString = 0.2.0`；`CFBundleVersion` 使用符合 Apple 要求的构建版本，不允许不同版本来源各自手填而漂移。构建时从统一版本输入生成/注入（至少检查一致性）。
- GitHub Release 附带**按架构准确命名**的 `.app.zip`（ZIP 根目录恰好一个 `Pata.app`，按实际包名统一），以及 `SHA256SUMS`。macOS `.dmg` 可额外提供手动安装，但不是 Updater 的输入；自动选择 release asset 时避免 `.dmg` 与 `.zip` 混淆。
- CI / 发布步骤：构建 → Developer ID 签名 → notarize/必要的 stapling → 验证签名与 Gatekeeper → 打包 ZIP → 生成校验和 → 创建 GitHub Release。所需 Apple 凭据仅存 CI secrets，不能进入 Git。
- GitHub provider 的 `ChecksumAsset` 负责 SHA-256 摘要校验；注意**摘要校验不等于独立可信的发布签名**。第一版至少保证 HTTPS、SHA-256、Developer ID 签名、公证和端到端验证；如需抵御 Release 渠道被攻陷，补充 Updater 可验证的独立公钥签名和对应发布源适配，不得把哈希校验描述为签名。
- 正式应用放在用户可写且可替换的标准安装位置（通常为 `/Applications`，在权限不足等场景应明确提示、不要假装更新成功）；开发/不可写目录不强制替换。

## 四、macOS 原生应用菜单（015-004）

- 目标是**屏幕左上角系统菜单栏的 Pata 菜单**，不是屏幕右上角的 Pata 状态栏图标；右上角状态栏点击唤起窗口的现有行为不在本阶段改造。
- 保留 macOS 标准 About、Services、Hide、Quit 等菜单行为。检查 Wails 默认/角色菜单项是否已经包含 Preferences，**优先接管现有项，避免出现两个「设置…」**。
- 「设置…」：快捷键 `⌘,`，唤起/聚焦现有 Pata 主窗口并进入 **SettingsView**，复用当前编辑草稿和页面离开保护，不打开独立设置窗口；与侧栏设置按钮的行为一致，避免与 React 现有 `⌘,` 处理重复冲突。
- 「检查更新…」：即使用户关闭自动检查，也可以在**官方正式安装版**手动调用一次检查。发现新版本时侧栏按钮出现或保留；已是最新版本时轻量提示；检查失败时提示可重试。开发/个人构建提示不可应用内更新。手动检查不直接触发下载、不打开版本详情弹窗。
- 退出与更新安装重启仍遵守编辑数据安全约束。

## 五、分批实施和验收

| 015-002 | Wails Updater 集成 | 生产版启动及定时静默检查、手动检查、用户点击才下载、校验/暂存、重启、失败重试均正确；无框架默认弹窗 |
| 015-003 | GitHub Releases 发布链 | 版本一致、正确 ZIP asset/摘要、签名/公证、CI 发布；正式可分发而不只是本地 ad-hoc 包 |

| 015-005 | 自动化与 macOS 真实升级验收 | 旧版→新版原位更新成功；草稿、权限、下载失败与签名失败等关键情形经验证 |

### 验收清单

- [ ] 正式发布版默认开启「自动检查更新」，可关闭并跨重启持久化；关闭时后台不再请求/提示；不增加自动下载/安装选项。
- [ ] 手动「检查更新…」在关闭自动检查后依然可用；开发/个人构建明确禁用官方自动更新与自替换，即使版本号一致也不会误替换开发环境。
- [ ] 无新版时设置旁没有更新按钮；有新版时仅出现一个更新入口，Vault 异常提醒仍可用。
- [ ] 点击更新立即开始下载；按钮实时显示正确的 0–100% 下载进度；无详情弹窗和「准备安装」文案。
- [ ] 下载到 100% 后经验证与暂存才可重启；没有未保存草稿时更新并重新启动，启动后显示正确新版本。
- [ ] 存在未保存 Note/Task/Activity 草稿时按钮为「等待安装」，后台绝不强制重启；保存后**不会自行重启**，再次点击才安装。
- [ ] 人工「检查更新…」已最新/网络失败反馈正确，任何后台检查都不会直接下载。
- [ ] macOS 左上角 Pata 菜单有可用的「设置…」「检查更新…」，保留标准菜单和 ⌘,，不误把托盘图标当作应用菜单。
- [ ] 正式 Release 的 ZIP、SHA256SUMS、版本号及签名公证均正确；至少从一个真实旧版安装包演练更新。
- [ ] 更新失败旧应用可运行，原 Vault 内容、关联文件、设置、Agent/MCP 正常；不修改数据格式。
- [ ] `go test ./...`、`npm --prefix frontend test`、`npm --prefix frontend run build`、macOS 打包与实机 UI 验收通过。
